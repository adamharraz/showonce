# Component references — 13 October 2026

**Current workflow:** after testing photo-to-3D reconstruction, the component catalogue is restored as the main 3D interface. Gemini selects a supported component family from a requested camera snapshot, the browser loads its prepared reference, and the user confirms or corrects the suggestion. SF3D generation is disabled in the local configuration. Its experimental source and existing private photo/mesh records are preserved separately; catalogue use makes no Modal or Stability request.

Open `/coach`. Before starting, browse the ESP32, breadboard, LED, axial resistor and jumper-wire reference models. Rotate/zoom with the mouse or touch. Model rendering runs locally in the browser with Three.js; it requires no GPU hosting, mesh-generation API or additional cash spending.

During a live session, show the components clearly and choose **Identify visible parts**. One current snapshot is attached to an ordered turn on the existing `gemini-3.8-live` connection. The model selects supported catalogue IDs through `show_components`. The server validates the IDs, evidence source, requested frame ID, freshness and scene revision before replacing the inventory. Unsupported objects can use an explicit unknown placeholder. The model can ask clarification questions; it cannot confirm an exact board variant or mark lesson checkpoints passed. Catalogue browsing remains available alongside the suggestions, so a failed match does not prevent viewing another reference. Browsing a generic ESP32 never inherits a confirmed pin layout from a different item.

Realtime image preprocessing can lag behind text. The first real test sent those inputs separately and the model replied that no snapshot was available. The implementation now binds image and request in one ordered turn. Audio/video forwarding is held during that inspection turn; the browser still shows a live camera preview. Microphone sharing resumes after the reply completes. Inspect when the assistant is idle. This keeps the snapshot and question together, using the same Live model without a second model or connection.

Use **Correct or confirm this part** to correct the family, confirm a supported exact board variant, supply a checked value/label and record how it was established. Corrections are owner-only and reject stale revisions. User-confirmed values retain their provenance. Blank values stay unknown. A new camera inspection replaces the inventory and requires new confirmation.

Only the explicitly confirmed **ESP32 DevKit V1 30-pin** variant exposes its reference pin selector. Choose a pin to highlight it on the model. ESP32/WROOM family recognition alone does not reveal a pinout. Other boards remain generic. Pin metadata comes from the pinned Wokwi Elements source linked in the interface; see `THIRD_PARTY_NOTICES.md` for the MIT notice. The generic ESP32 now uses the user-supplied “ESP32 Wroom” USDZ by TER1Z (CC BY 4.0), with visible attribution. Its mesh has 38 header contacts, so it is not used for the 30-pin variant's pin mapping. Selecting that confirmed variant displays the separate nominal 30-pin procedural reference. Other components remain procedural. Imported silk-screen lettering is hidden in the generic preview; its appearance is not physical-board or pinout verification.

Models are illustrative: their colour, dimensions, lead lengths, hole count, wire curve and pose do not measure the real object. The panel does not reconstruct a circuit, simulate electricity, verify continuity or infer hidden endpoints. Required assembly instructions and checkpoints still come from the instructor's demonstrated/reviewed lesson; the catalogue contains no target circuit checklist.

The ESP32 reference now uses a millimetre-based nominal layout (0.1 scene unit/mm on every axis): 54 × 27.9 × 1.6 mm PCB, 15 contacts per side at 2.54 mm pitch and 22.86 mm row spacing. The frontend geometry and backend pin coordinates use the same centred-grid formula, preserving the pin IDs and order. Contacts extend from the PCB to the nominal 8.5 mm header height; highlight rings sit at the housing top. Mounting holes are actual 3.2 mm through-holes.

This is not a verified mechanical reproduction. [Wokwi's board graphics](https://github.com/wokwi/wokwi-boards/blob/main/boards/esp32-devkit-v1/board.json) confirm 2.54 mm pitch but use differing board/row dimensions; the requested PCB dimensions and 22.86 mm row spacing remain nominal user targets. [Espressif's module datasheet, section 9](https://www.espressif.com/sites/default/files/documentation/esp32-wroom-32_datasheet_en.pdf) verifies the **complete** WROOM-32 module envelope of 25.5 × 18 × 3.1 mm, including the antenna. The model uses an assumed 6 mm antenna region and a 19.5 mm shield body within that envelope. Its 1.5 mm overhang, shield split, header/contact construction, 6 × 6 × 4.5 mm buttons and hole centres remain unverified assumptions. USB and CP2102-like footprints/longitudinal centres preserve the old geometry's nominal dimensions. These references do not confirm the physical board, its pinout or continuity; the supported-variant confirmation gate still applies.

The component inventory is saved privately with the conversation for seven days. Snapshot pixels stay in memory, so historical frame IDs/timestamps are metadata rather than retained image evidence. Opening saved references or browsing models makes no Gemini request. An explicit inspection consumes Live quota; the free-tier account guard, ten-minute session limit, 40-reply cap and daily application guard remain. The removed 200,000-token cap does not apply. There is no paid fallback.

## Validation

Automated tests cover invalid catalogue IDs, prohibited model variant confirmation, stale frame references, absent camera evidence, unreadable values, owner-only corrections, stale edit rejection, saved history and no changes to formal checkpoint assessments. The current regression run passed 80 backend tests, seven frontend tests and the production build. `scripts/browser-component-test.cjs` passed with a synthetic camera and an explicitly isolated component fixture: all five models, unknown values, browsing after recognition, manual variant confirmation, pin highlighting, fresh-inspection confirmation reset, chat, pause/resume, saved history and desktop/mobile layout. It asserted that no GPU-generation request was made. WebGL failure keeps text metadata available.

One real `gemini-3.8-live` test used an unlabelled synthetic drawing of an LED and axial component. The corrected transport produced a valid tool call in about **2.42 seconds**, selected LED plus an uncertain resistor, left values unknown and requested a clearer resistor view. One completed reply reported **2,100 tokens**. These are individual synthetic integration results, not a physical recognition accuracy or end-to-end latency benchmark. The initial failed attempt reported 1,844 tokens. Both tests used the owner's existing confirmed Free-tier project; billing and paid fallbacks were not enabled.

The restored interface was checked against the owner's actual ESP32 photograph that SF3D had misinterpreted. The first Live attempt emitted rejected tool responses and ended with a request for a clearer view; no inventory was changed. The tool schema now explicitly guides short valid component IDs and exact frame-ID copying, and rejected calls record only safe field paths/error types or fixed guard reasons, without raw model arguments or image data. A repeat inspection returned one ESP32 family suggestion in **1.416s**, with **2,077 reported tokens**, no invented value, no confirmed variant and a request for readable pin labels. It ran on the existing Live model without a GPU or fallback model. The exact cause of the first rejected calls was not captured, so this is a passing repeat rather than proof of consistent recognition.

Broader ESP32/breadboard photos, different board variants, occlusions, component counts and physical teaching accuracy still require labelled validation. No TRL4 claim follows from these tests.
